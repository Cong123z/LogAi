# Memory probe: before (master e8ec04b) and after (build/pattern-switch)

## Before (master e8ec04b)

`scripts/mem_probe.py` rebuilds one service `vas` (N templates, 48 baseline rows each, a Drain3 blob of N clusters,
5 committed weekdays) in a throwaway schema, then a child process builds `Owner` and measures. Detection is off in the
probe, so the flush numbers are a floor.

What each number includes: `load_peak_mib` is the peak RSS while `Owner` loads (before `trim()`); `load_steady_mib` is the RSS
after `trim()`; `save_state_ms` is `Miners.dirty()` after one new cluster; `flush_peak_mib` is the peak of the WHOLE run (load,
holding M open minutes, closing, flushing), not the flush alone, so it is never below `load_peak_mib`. Holding M open
minutes with the watermark held is not reduced by the bites (see B29). The flush step holds the watermark for M minutes (one count per template per
minute), then moves it past all M in one batch and flushes (the B25 shape).

Laptop: 13 GB RAM, ~3.3-3.8 GB available, swap full (the Docker VM holds bge-m3 and ES). The full-size run
(`--templates 135000 --minutes 1300`) was NOT run, by the tech lead's ruling; sizes run one at a time with a kill guard at
3000 MiB RSS.

|---|---|---|---|---|---|
| 20,000 | 32.3 KiB | 690 B | 26.2 KiB | 19.8 ms | (1180.4-631.5) MiB / 2.4M = 240 B |

| 80,000 | 30.4 KiB | 648 B | 24.2 KiB | 29.3 ms | not measured (killed >3000 MiB) |

Load is linear in templates (slightly sub-linear per template); the Drain3 save grows a little faster than linear.
The flush holds one open minute per template-minute, ~240-245 B each, on top of the load.

| quantity | extrapolated |
|---|---|

| load_steady_mib | 135000 x 24.2 KiB = ~3,190 MiB |
| save_state_ms | ~4-5 s per Drain3 save (grows slightly faster than linear)

None of the 135k figures was run. The 80,000 x 120 kill is consistent: 2372 + 80000 x 120 x 245 B = ~4,600 MiB, above the guard.

## After (build/pattern-switch 23ed042: pm1 packed baseline, pm5 bites, pm3 active services)

Same probe, same laptop (available RAM 2.4-2.8 GB, below the 3000 MB rule: the sizes run have estimated peaks of
0.4-1.3 GB, so each was run one at a time with the 4000 MiB kill guard, which never fired).

### Before / after (MiB)

| templates | load_peak before -> after | load_steady before -> after | flush_peak, 120 min, before -> after | save_state before -> after |
|---|---|---|---|---|
| 20,000 | 631.5 -> 150.0 | 512.6 -> 130.2 | 1180.4 -> 611.9 (pm5 alone: 1000.0) | 396 ms -> 550 ms |
| 40,000 | 1211.8 -> 219.4 | 972.7 -> 196.6 | 2332.1 -> 1215.6 | 924 ms -> 1443 ms |
| 80,000 | 2372.1 -> 382.5 | 1892.5 -> 340.4 | not run (killed) -> not run (`--minutes 1`: 398.4) | 2347 ms -> 2437 ms |

Off switch, 40,000 templates (1.92M baseline rows): the process is 52.9 MiB with the pattern Off at start, 196.9 MiB On,
70.7 MiB after Off again (the 18 MiB above the start is Python heap that is not returned). At 20k (pm3): 52.7 / 130.4 / 68.9.

What changed: the packed baseline brings the load from ~650 B to ~80 B per baseline row (load_peak 6x smaller at 80k). The
flush part is about 200-217 B per template-minute (was 240-245 B): the bites and the sample cap only bound the closing part,
the open counts of M held minutes stay in memory until the watermark moves. `save_state_ms` is not better: the packed
baseline does not touch the Drain3 tree, and the Drain3 save is still the whole tree (B27); the 20k/40k differences are
laptop noise on top of a ~25 ms per 1k templates cost.

### Extrapolated, not measured: 135,000 templates / 6.48M baseline rows (after)

Linear, from the 80,000 row (load) and ~217 B per template-minute (40k x 120, (1215.6 - 219.4) MiB / 4.8M).

| quantity | extrapolated |
|---|---|
| load_peak_mib | 135000 x 4.9 KiB = ~645 MiB (before ~4,000) |
| load_steady_mib | 135000 x 4.4 KiB = ~575 MiB (before ~3,190) |
| save_state_ms | ~4-5 s per Drain3 save (B27) |
| flush_peak_mib, 120 minutes held, every template every minute | 645 + 135000 x 120 x 217 B = ~4,000 MiB (before ~7,800) |
| flush_peak_mib, 1,300 minutes held, every template every minute | 645 + 135000 x 1300 x 217 B = ~37,000 MiB (before ~45,000) |

The last two rows are the worst case of the probe shape (every template counted in every held minute). They show that the
bites do not make holding open minutes cheap (B29). What removes the incident is the switch: with the pattern Off the
135k-template service is not loaded at all (the process stays near the 53 MiB start), and a start with it On needs ~0.65 GiB,
not ~3.9 GiB.
