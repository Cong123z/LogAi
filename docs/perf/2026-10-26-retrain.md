# Re-read lane: truth and stress proof (2026-10-26)

Script: `scripts/stress_pipeline.py`, scenarios `R1`-`R4` (by name only, not in `all`).
`tests/test_stress_pipeline.py::test_stress_pipeline_reread_tiny` runs R1, R3, R4 at `--scale tiny`.
Same harness as [2026-10-24-pipeline-stress.md](2026-10-24-pipeline-stress.md): the real `Engine`, an injected
clock, a generator source with a modelled ES latency, a throwaway schema per run.

## How it works

The generator holds 3 days (D1 = 2026-10-21 re-read, D2 live, D3 "today"); `now` is D3 00:05, so D1 and D2 are
already in "ES". Two patterns: `stress-*` (one index per service) and `extra-*`; svc00 is fed half by each, and
`extra-svc00-1` holds D1 before 18:00, `extra-svc00-2` the rest (R4 deletes `-1`). `GenSource` gained `count`,
`oldest_ms`, `page(..., timeout)` and `delete_index`. Truth ("schema A") is a live read of D1+D2 into a schema,
shared by R1, R3 and R4. Rows are compared per table (`service_hours`, `hourly_counts`,
`template_module_hours` for D1) and `baseline` after a nightly-style rebuild in both schemas, **by template text,
not id** (Drain3 numbers by first appearance; here both schemas start from the same pretrained Drain3, but the
comparison does not depend on it). Time is simulated as in the 10-24 doc; lane rates are per simulated second.
- R1: B = live D2, then re-read of D1 (all services, 00-24), vs A.
- R2: live at 10k ev/s while 6 h of D1 are re-read; lag, late counts, lane rate, pauses.
- R3: engine "killed" (connections closed without a flush, new `Engine` on the same schema, `start()` resumes) at
  30 % and 70 % of the D1 re-read; rows vs A, state, `pos_ms` sampled every tick.
- R4: `extra-svc00-1` deleted at 50 %; run log must carry the retention warning, hours after the deleted range
  must not be zero where truth is not, other services fully written.

## Machine

AMD Ryzen 7 8845H, NVMe, Linux 7.0, PostgreSQL 16 (Docker, defaults), Python 3.11. R1/R3/R4 below ran with the
local logai2 stack stopped (logai-engine, another project, kept running).

## Commands and results

Default scale (10 services x 300 templates, 2,000 ev/s) did not run for R1/R3/R4: the disk guard refused it
at ~1.2 GB free (7.8 GB estimated), and with 73 GB free it still needs 2 days x 2,000 ev/s = 345M events for
schema A alone (hours). They ran at the **largest scale that fits the time box: 10 services x 20 templates,
50 ev/s** (8.67M events for the 2-day truth, 4.32M docs in D1).

### R2 (10 services x 300 templates, 2,000 ev/s past data, 10k ev/s live, 6 h): to re-run at default scale with the engine stack stopped (open)

First run (the live logai2 stack was competing for Postgres and CPU; older script without the peak instrumentation):
state succeeded; re-read counted 43,200,000 = truth; live counted 24,600,000 = truth; late 0; lag p50/p95/max
30.6 / 31.7 / **188.4 s** (target < 90 s: **missed**); lane 17,350 docs/s sim (7,153 wall incl. generator); 357
paused ticks; 6,039 s wall. Cause of the 188 s peak unknown: one spike, p95 is 31.7 s.
Re-run at `--r-eps 200` (4.3M past docs), stack running: lag 30.9 / 31.3 / 34.3 s, 0 s above 60, late 0, lane
19,790 docs/s sim, 20 paused ticks, baseline rebuild 3.1 s (so the end-of-run rebuild is not the spike), counts exact.
The spike is not yet reproduced; no BUGS entry until the default-scale re-run shows it again.

## Findings

- Re-read equals live reading exactly (R1), survives two crashes (R3) and a deleted index (R4: skipped, not
  zeroed, warning in the run log).
- R2 lag spike at default scale: open, see above.
- The disk guard counts every backlog minute of a 2-day catch-up; a "schema A" truth run at default scale is
  hours long and was not attempted.
